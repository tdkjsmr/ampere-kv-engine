### [2026-09-17] INT8 KV 性能分支：定位"量化后延迟反而更高"的根因

- **作者**：平台q（只读诊断，未改动代码）
- **阶段/分支**：测量性能；`main` @ `8fd1075`
- **动机**：RTX 3090 上执行 `--mode benchmark --cache paged --kv-dtype int8`，INT8 KV 的延迟高于 BF16 CUDA，需定位原因并决定该分支后续走向。
- **修改的模块与文件**：无。本次仅阅读代码与运行输出，未产生文件改动。
- **改动要点（诊断结论，三条互相独立）**：
  1. **收益上限近乎为零**：Qwen3-8B BF16 权重约 16.4 GB，每个 Token 必须完整读一遍；52 Token 上下文下 attention 的 K/V 读取仅约 7.7 MB，占 0.047%。Decode 是权重带宽与启动开销受限，不是 KV 带宽受限。即使 KV 读取降到 0，每个 Token 也只省约 4 µs，而实测 TPOT 为 48819 µs（Amdahl 定律：加速对象本身不是瓶颈）。
  2. **反而变慢来自热路径上的参考实现**：`PagedKVCache.append`（`ampere_kv/paged_cache.py:74-82`）在每层每 Token 调用 `quantize_kv`，而该函数在 `ampere_kv/quantization.py:1,11-12` 中自我声明为"不接入缓存、不用于性能计时"的参考实现。它内部含两处 `.item()` 设备同步（`quantization.py:17,27`）与约 18 个逐元素小 kernel。36 层 × K/V = 每个 Token 约 1300 次额外 kernel 启动 + 144 次**额外**设备同步。

     **BF16 路径本来就有设备同步**：`paged_decode_impl` 的块号检查（`csrc/paged_decode.cu:199-202`）每次调用 `min().item()` / `max().item()` 各一次，两个精度入口共用同一段代码，因此 BF16 每 Token 同步 72 次、INT8 216 次。差别不在于同步的有无，而在于**同步之后 GPU 有多少活可干**：

     - BF16 每层的块号检查之后，紧跟着约 50 个算子、约 1.0 ms 的真实 GPU 计算，CPU 的 Python 派发被掩盖在 GPU 执行时间内；
     - INT8 每层被 6 次同步切成 5 段，其中量化区域操作的是 1024 元素的小张量，GPU 实际计算约 25 µs，而 PyTorch 派发那 18 个算子要约 250 µs——**GPU 空转等 CPU**。

     按每层两次量化、每次约 250 µs 空转粗估，整 Token 约 +18 ms（**代码推断，未测量**；精确拆分需要 profiler 或逐区域计时）。
  3. 次要：INT8 内核每 Token 多出 5 次 shuffle + 8 次 cvt + 8 次 fmul（`csrc/paged_decode.cu:67,92`），量级可忽略；**内核未见退化证据，但项目从未单独测过 INT8 内核**（`ampere_kv/paged_decode.py:150` 注明 `--benchmark` 不测 INT8）。
- **容量事实**：计入 FP16 scale 后，INT8 KV 相对同容量 BF16 约 **1.93×**（scale 占 7.8% 开销）。当前 INT8 的真实收益是**容量**，不是单请求延迟。
- **验证状态**：结论来自代码审查 + 用户提供的 3090 运行输出。BF16 侧为实测数据（TTFT 中位数 73.862 ms，TPOT 中位数 48.819 ms，总耗时中位数 1586.500 ms，输出吞吐中位数 20.170 Token/s）。**INT8 侧完整计时数字尚未取得；"变慢约 +18 ms/Token"为代码推断，未测量。**
- **性能影响**：本次无代码改动。
- **遗留问题 / 下一步**（对齐方案文档第 1556 行"保留容量贡献，分析临界 Context；优化融合而非编造加速"）：
  1. 给 `paged_decode --benchmark` 补 INT8 算子级基线（length=64/256/1024），把"内核账"与"端到端账"分开。
  2. 去掉热路径上的 `.item()` 同步（至少移出计时路径），让 INT8 不再倒亏。
  3. 实现方案第 681 行的 V1 量化写入融合，把每 Token 72 次参考量化调用 + 144 次额外同步压成 36 次内核启动，量化侧同步归零（块号检查的 72 次共用同步属另一项优化，需单独处理）。
  4. 扫描 Context 找收益边界；对 8B / 3090 单请求，KV 字节追平权重字节约在十万 Token 量级，远超本机容量——这本身就是结论。
- **禁止事项**：不得把本分支结论写成"INT8 更快"。

### 2026-09-20 内部Decode路径移除逐层块号标量取回（待云端验证）

- **作者**：平台q（只改代码，本机无CUDA，未编译未运行）
- **动机**：`paged_decode_impl`每次调用对有效块表做`min().item()`/`max().item()`两次标量取回，Decode每Token 36层×2=72次CPU等待点（2026-09-17台账已记过该数字）。按Codex裁定：要消除的是这些逐层取回造成的等待，**不是物理块编号的边界约束**。
- **改动**：`paged_decode_kernel`增加物理块总数入参，在读取`physical`之后、任何K/V或scale访存之前用`CUDA_KERNEL_ASSERT`拦截`0 ≤ physical < 块总数`；`paged_decode_impl`增加`check_table`形参，把宿主min/max检查改为条件执行，其余形状/类型/设备/长度/块表长度检查仍无条件执行；新增`paged_decode_internal`与`paged_decode_int8_internal`两个内部入口并在`bindings.cpp`注册。
- **受检查入口保留**：`paged_decode`/`paged_decode_int8`行为不变，供独立算子检查与外部调用；`paged_decode.py`原有的非法块号测试仍打在受检查入口上，仍是可捕获的同步异常，"非法输入立即报错、进程还能继续做其他检查"的行为没有被悄悄改变。
- **错误处理语义差异**：内部入口"仍防止越界访问"**不等于**"仍保持原来的同步异常行为"。设备端断言属异步失败，通常在后续同步点才可见；发生后不能捕获异常继续复用同一CUDA上下文，后续CUDA调用都会失败。因此内部路径出现非法块表视为实现错误，失败后终止该运行；本轮不做可恢复GPU错误框架。
- **保护能力边界**：块号处于合法范围不代表属于当前请求；原来的min/max检查同样没有验证请求归属，归属仍由块池与块表生命周期保证。不得夸大新旧检查的保护能力。

### 2026-09-21 V3 原型：同组四个 Query 头共享一次 K/V 载入（已实现，未编译未测量）

- **作者**：平台q
- **动机**：V1 之后 INT8−BF16 还剩约 4.3 µs 且与长度无关，同时同一 KV 头的 K/V 仍被四个 Query 头各读一遍（预注册假设 H2）。V3 把一整组四个 Query 头放进同一个线程块，验证寄存器内复用能否换来正收益。
- **分工与复用**：`blockIdx.x` 由 Query 头号改为 GQA 组号，块内仍是四个 warp 交错处理段内 Token，每线程持有连续四维 × 四个头（16 个 FP32 累加器与 16 个 query 分量）。每 Token 的块表读取、K 行与 V 行载入、两份 scale 广播和 INT8 反量化都只做一次，四个头各自点积、各自 warp 归约、各自维护在线 softmax 的 max/分母/累加器，**softmax 不跨头混合**。每头的算术次序与 V1 逐项相同，所以结果差异只应来自编译器取舍。
- **与 V1 的关键差别**：V1 内核**一行未改**，继续作 A/B 基线和非 4 倍 GQA 的回退；段长 64、partials 布局 `[Query头, 段, 130]`、跨段 merge 内核、stream、有效长度与尾段语义全部不变。新增 `paged_decode_v3_kernel<KV>`，BF16/INT8 仍共用模板。
- **预期代价（未验证，须云端确认）**：静态共享内存 2080→8320 字节；每线程多 12 个 query 与 12 个累加器分量；**网格横坐标 32→8，块数降为四分之一**，短上下文可能因并行度不足反而变慢。不预设 DRAM 流量除以四就等于提速。
- **选择方式与保护**：四个入口新增末位 `v3` 参数，默认 `false` 仍是 V1，未测量前不替换默认路径，也没有长度阈值自动选择。`v3=true` 时宿主先检查 `q_heads == kv_heads * 4`，**不支持的配置直接报错而不是静默退回 V1**，这样"跑通了"本身就证明用的是四头内核；内核内 K/V 与 scale 访存前的块号断言保留。模型侧加 `--decode-kernel {v1,v3}`，`cuda-check`/`int8-check`/`benchmark --cache paged`/`generate --kv-dtype int8` 会实际调用 V3（`main` 拒绝把 v3 用在不会走 CUDA Decode 的组合上，避免把 SDPA 或 V1 的结果当成 V3）。
- **验证状态**：本机无 CUDA，**未编译、未运行任何检查或测量**。已做 AST 解析、`git diff --check` 与静态索引核对。**云端待执行**：默认算子检查（新增 4 倍 GQA 的 V3 对照与非 4 倍请求被拒绝两项）、`--benchmark`（长度 64/256/1024/4096，同轮内 V1/V3 交替，报中位数与极差）、一次性 `cuobjdump -res-usage` 看寄存器/共享内存/是否溢出、`--mode check --cache paged`（补上轮 V1 模型级未重跑）、`cuda-check --cache paged --decode-kernel v3` 与 `int8-check --cache paged --decode-kernel v3`。正确性通过前不谈性能；算子变快不等于模型 TPOT 提升。

### 2026-09-21 G6-A 多请求生命周期骨架（已实现，本机未运行任何检查）

- **作者**：平台q
- **目标与边界**：让多个请求共用模型与每层物理 KV、各自保有自己的历史、交错生成、完成后归还、新请求能复用回收的块。这一轮建立的是**多请求执行骨架**：每个调度轮次仍是逐请求调用模型，没有把多个 Token 合成一次 GPU 批量计算，**不构成 Continuous Batching，也不做任何吞吐提升承诺**。
- **结构**：新增 `ampere_kv/scheduler.py`，只有 `Request` 与 `Scheduler` 两个对象；状态仅"等待/活动/完成"三态，EOS 与达到上限只记在 `stop_reason`。没有策略基类、注册器、事件总线、锁、事务或引用计数。
- **所有权**：每层一个共享 `PagedKVStorage`（物理张量与空闲块池被所有请求复用），每个请求持自己的 `BlockTable`。**共享的是空闲池，不是已经分配给某个请求的块**——分配出的块仍由所属请求独占，所以不需要引用计数。释放只发生在 `_retire` 一处，`BlockTable.release` 本身可重复调用。
- **调度顺序**：①活动请求各执行一次 Decode → ②有停止原因的请求立即退出活动集合并归还块与额度 → ③至多接入队首一个新请求（每轮一个）→ ④新请求执行完整 Prefill 取得首个 Token → ⑤首个 Token 就满足停止条件则直接完成，不强行进入 Decode。FIFO，不跳过队首、不抢占已在跑的请求。
- **容量管理**：提交时按每层 `ceil((输入 Token + 生成上限 + 1) / 块大小)` 预留额度（多留一个 Token 覆盖"决定末位 Token 的那次 Decode 已写入 K/V"），准入条件是比较**预留额度之和**与每层块数，而不是看当前空闲块——只看空闲块会让多个请求同时消耗尚未兑现的增长空间，最终在 Decode 中途耗尽块池。预算超过整层的请求在提交边界直接拒绝，不留到永远等待。**预留额度不写进 `BlockTable.length`**：有效长度仍然只表示真正追加的 Token。
- **复用与未改动**：`runner.py` 只抽出 `encode_prompt` 与 `load_model_and_tokenizer` 两个入口供调度器共用（不复制生成逻辑），其余行为未变；缓存、块池、CUDA 内核（V1/V3）、量化规则、Attention 数学与容差一行未动。调度器每步只有 argmax 之后那一次 `.item()`，那是选词停止判断本身需要的同步；没有为检查新增每层同步、有限性扫描或块表扫描。
- **云端验收入口**：`python -m ampere_kv.scheduler`（需要 GPU 与已编译扩展，无参数，加载一次模型跑完四组检查）。四组验收分别是：①A/B/C 交错生成与分别单独运行的完整 Token 序列一致（同 BF16/V1 路径）；②r0 提前完成不影响 r1 继续生成；③r2 复用 r0 归还的物理块编号且序列与独立运行一致（没读到别人的旧历史）；④容量与回收正确——暂时装不下的请求留在等待队列、预算超过整层的请求被拒、全部完成后预留额度归零且每层的块全部归还。用例容量取 `max(r0,r2 预算) + r1 预算`，使"r2 必须先等待、r0 释放后必然可接入"不依赖具体 Prompt 长度。
- **验证状态（不得当作通过）**：本机 Windows 无 CUDA，**未运行任何一条检查**，只做了 AST 解析、`git diff --check` 与索引/所有权的静态核对。交错与独立一致、混写与越界是否真的不会发生，都要等云端首跑；这四组没全绿之前 G6-A 不算完成。
- **本轮明确不做**：GPU 批量 Decode（G6-B）、Chunked Prefill（G6-C，本轮 Prefill 仍只接受空缓存）、前缀复用/共享已分配块/换出/抢占、线程并发与网络服务、CUDA Graph、INT8 或 V3 的多请求接入、配置体系与调度策略接口。
- **风险与失败表现**：交错一致性的前提是没有跨请求写同一物理块。若所有权或预算记账有 bug，最先崩的应是"r2 与独立运行一致"或收尾的块归还断言；CUDA 侧错误不可恢复，设备端块号断言一旦触发本次运行即终止，不做 GPU 故障恢复设计。

### 2026-09-22 G6-B 批量 Decode：一组请求的当前 Token 合成一次模型前向（已实现，本机未编译未运行）

- **作者**：平台q
- **要回答的问题**：多个请求的一个 Token 能否合成一次模型计算。本轮做到：B 个请求各出一个新 Token，一次批量线性投影 + 一次批量分页注意力；每个请求保留自己的绝对位置、块表和有效长度。**历史既不读回连续显存也不跨请求拼接**——这就是真批量与"把各家 KV 摊平成一块连续 KV 再算"的分界。
- **内核**：`paged_decode_batched_kernel` 的网格横坐标是"批 × Query 头"，每块负责一个 (请求, 头) 对；块表是 `[B, 每请求最大块数]` 的定宽行，各请求的有效长度从**设备端** `starts` 读取（每步每请求写一个 Token，长度即起点 + 1），宿主不取回任何标量。段长 64、四 warp 交错、连续四维打包载入与五级归约台阶都和 V1 逐条相同，所以每个 (请求, 头) 的算术次序没有变化；跨段合并继续用原 `merge_decode_kernel`，只是行号从 Query 头号换成 (请求, 头) 行号。配套的 `bf16_write_batched_kernel` 用同一份行式块表一次写入 B 个请求的新 K/V，起点同样取自设备端。
- **分段数不读长度**：网格 y 维按块表行宽上界 `ceil(行宽 × 16 / 64)` 确定，超出某请求实际长度的分段整块空转，只写出全零局部结果，由跨段合并按"分母为零"跳过。这样就不必为拿 `max(length)` 做 `lengths.max().item()`——那是每层一次的宿主同步，正是前面花一整轮移除掉的成本。
- **越界保护**：两个内核在**读块表之前**先断言块内槽位小于行宽，再断言物理块号落在 `[0, 块数)`。填充列本来不会被读到（索引只走到各请求自己的长度），但定宽填充是 Python 侧算出来的，算错就是越界读，所以这条保护保留而不是当作冗余。
- **接口调整（计划书要求先说明的一处最小改动）**：`PagedKVCache.reserve(num_tokens)` 把"登记块表"与"融合写入"拆开，只登记并返回最新块表、不写 K/V。批量路径需要 B 个请求各登记一次、再由一个内核一次写完，而现有 `append` 把这两件事绑在一起。缓存布局、块池所有权以及 `append`/`get`/`release` 的既有语义一字未改；起点必须在 `reserve` 之前取，因为登记之后 `length` 已经含本步 Token。
- **模型侧**：`runner.py` 新增 `decoder_layer_batched_forward` 与 `model_forward_batched`。每层把"每请求一组缓存"转置成"每层一组请求缓存"，做一次批量写入 + 一次批量注意力，残差、MLP 与输出头沿用共用的后半段；选词在调度器里一次同步拿回 B 个 Token。单请求的 `model_forward`/`decoder_layer_forward` 未动。
- **调度器**：`Scheduler` 增加 `max_batch`，默认 1。`max_batch=1` 时走的仍是 G6-A 的逐请求 V1 路径，行为与上一节点完全一致，G6-A 的四组验收因此原样保留；`>1` 时把活动请求按块切分送批量前向，不足一整块的余量同样走批量入口。Prefill 仍是整段一次做完（改这个是 G6-C），每轮仍至多接入一个新请求。
- **验收**：`python -m ampere_kv.scheduler` 现在跑两组。G6-A 四组原样保留；G6-B 用五个历史长度互不相同的请求（把短句重复拉平成约 20/40/60/120 Token，跨过 16 Token 的块边界和 64 的分段边界），要求**三方一致**——单独运行、逐请求调度、批量 B=4 的 Token 序列逐个相等；并断言实际最大成块数真达到 4、确有请求中途等待接入、收尾预留额度归零且每层块全部归还。批量改变了线性层的执行形状（`[B,1,H]` 的 GEMM 与逐条 `[1,1,H]` 不保证逐位相同），所以按计划书不预设 logits 逐位相同；序列一旦不一致先定位原因，不放宽断言。
- **验证状态**：本机无 CUDA，**未编译、未运行任何检查**。本轮改了 `csrc/`，云端必须 `make build`；四组与三方一致全部待云端实测，G6-B 在拿到这些结果之前不通过。
- **本轮行数如实报告**：任务书未给 G6-B 预算，我按最小实现自定 420，实测 449 超出（两个批量内核与宿主入口 211、调度与验收 155、批量前向 45）。用户授权放行并把基线预算上调到 460；可压的只剩注释和边界检查，而计划书明确禁止用它们凑预算，所以没有砍范围，也没有借上调扩范围。
- **本轮不做**：INT8 与 V3 的多请求、批量 Prefill、Chunked Prefill、取消/超时统一回收、CUDA Graph 与静态块表缓冲（每步仍新建 table/starts 张量并重传，长上下文开销照旧，G6-E 之前必须收敛）、任何吞吐或延迟结论。

### 2026-09-22 G6-B 收尾：批量内核补请求级范围保护，调度器不再积累历史

- **作者**：平台q
- **补的保护**：两个批量内核在任何块表与 K/V 访存之前断言 `0 <= 起点` 且 `起点 (+本步 Token 数) <= 行宽 × 16`，仍是设备端断言、不引入宿主同步。此前循环内的"槽位小于行宽"挡不住**负起点**——负数天然小于行宽会通过断言，紧接着 `row_table[负]` 就是越界读；现在负起点在入口就被拦住，循环内那条冗余断言随之删掉（入口范围已保证 `token < length <= 行宽 × 16`），热循环少一次判断。物理块号断言保留不变。
- **调度器去掉 `submitted`/`completed` 两个永久列表**：它们会让长期运行的引擎无上限积累元数据，而引擎本身不需要这些历史。`step()` 改为返回 `(本轮完成的请求, 每批实际处理的请求数)`，结果由调用方自己留存；验收在调用方保存请求引用，三方序列对照的语义不变。
- **真实批量大小改从调用处记账**：不再用"轮末活动队列长度"反推成块数——同一轮末尾还会接入新请求，用队列长度会把没参与这次批量 Decode 的请求也算进批里。现在 `_decode_round` 在真正调用前向的地方记录每组大小，`max_batch=1` 的逐请求步记为 1。
- **新增 `check_batched_operator()`**：不加载模型，一次启动放写入后长度为 1/17/65 的三个请求（短历史、跨 16 Token 块、跨 64 分段），对照同一条连续 K/V 的 FP32 参考 Attention（容差沿用既有算子检查的 `rtol=0.01, atol=0.002`，未放宽），并逐位检查"本步 K/V 落在每个请求自己的起点槽位"和"起点后第一格仍是 NaN 哨兵"（证明没有多写一格）。块表填充列填 **-1**：内核只要读到填充列就会在设备端断言上失败，所以"通过"本身就证明填充列没被读。原来的六个 INT8 场景确实不覆盖这两个新 BF16 批量内核，这是补上的缺口。
- **过时标签订正**：benchmark 后端标签 `CUDA V0` → `CUDA V1`（`CUDA V3` 不变），`cuda-check` 的错误信息去掉 V0，两条宿主 `TORCH_CHECK` 文案里的 "V0" 改成中性措辞。只改字符串，未动逻辑、量化规则、容差与 V1/V3 算法。`csrc/bindings.cpp` 里还有一处 pybind 说明写着 `Decode V0`，不在本轮白名单内，留到下一轮顺手改。
- **非法起点保护的验证方式**：设备断言会毒化 CUDA 上下文，所以**不写常驻子进程测试**；由云端一次性独立进程验证（命令在交接里），跑完即弃。
- **验证状态**：本机无 CUDA，未编译、未运行。云端需 `make build` 后重跑 `python -m ampere_kv.scheduler`（新算子对照 + G6-A 四组 + 三方一致，且算子对照排在最前，不加载模型就能先失败）。本轮不引入任何吞吐测量，性能基线是任务二。
- **行数如实报告**：任务书建议约 150 行，实测约 170 超出。原因是新批量算子对照本身要建块表、写历史、逐请求对照参考并检查写入位置（48 行），加上 `step()` 返回值改造；可压的只有注释，按"明显超出先说明原因"处理，没有删说明凑数。
- **补的对照第一次上云就失败，失败点在我自己写的测试代码**：`check_batched_operator()` 用 `torch.stack` 拼 `[1, KV头, 1, 128]` 切片，得到五维张量，被批量写入入口那条"必须是四维"的边界检查直接拒绝（`RuntimeError: 批量写入输入必须是 CUDA [批, KV头, Token, 128]`）。`make build` 已通过，所以内核与宿主入口都没错；改成 `torch.cat(..., dim=0)` 即得 `[批, KV头, 1, 128]`。生产路径本来就没这个问题——它的 K/V 直接就是四维 `[B, KV头, 1, 128]`。这次也正好说明边界检查留着的价值：错误在进内核之前就报出来，而不是变成一次越界或难查的数值偏差。

### 2026-09-22 G6-B 任务二：批量收益与 Prefill 干扰两组受控基线（已实现，本机未运行）

- **作者**：平台q
- **为什么单独一个文件**：新增 `ampere_kv/bench_scheduler.py` 只做实验驱动与统计。`scheduler.py` 里已经有不少验收代码，再把性能场景、打印与统计塞进调度主线会让两边都难审阅；这里也不引入 benchmark 基类、配置系统或自动报告框架。调度器本轮只多一个开关：`submit(..., ignore_eos=True)`，用来固定工作量（正常生成仍遇 EOS 停止），逐步计时全部在实验文件外部完成，普通生成不保存任何逐步历史。
- **实验 A（纯 Decode）**：固定 BF16 与默认 V1 系列路径、同一张卡；历史长度固定（默认 512 Token），Prefill 全部在计时外完成，然后计时 64 个纯 Decode 轮，重复 3 次报中位数与极差（同时给"重复之间的极差"和"单次内轮间极差"）。B 取 1、2、4、8，每个 B 都比"同样数量请求逐条 Decode"与"批量 Decode"两条路径；B=1 时两条路径是同一次内核调用，只测一次不造两条相同曲线。计时包含模型前向、KV 追加、块表等元数据上传、选词与必要同步。
- **口径红线（写进代码注释与打印）**：每轮墙钟就是每个请求两次输出之间的间隔；吞吐 = 本轮推进的请求数 ÷ 每轮墙钟。**批量轮次耗时 ÷ B 是吞吐折算，不是用户 TPOT**，程序里每个 B 都会把这句话打印一遍，避免以后被误引。`B=8` 没有既有正确性证据，测量前先跑一次计时外结果检查（批量与单独运行 5 个 Token 序列逐个相等），不把"B=4 通过"外推过来。
- **实验 B（Prefill 插入干扰）**：固定 4 个活动请求在解码，第 32 轮插入一个新请求（输入 512 与 2048 Token 两档），仍用完整 Prefill、不改调度策略。记录新请求从提交到首 Token 的墙钟（含等待）、原有请求插入前后的每轮间隔、插入后被拉长的倍数与整段每轮中位数。容量按"提交后当轮即可接入"配好，所以**测的是完整 Prefill 本身的阻塞，不含排队**——这一点在打印里写明，避免把两件事混成一个数。样本少，只报原始值、中位数与最大值，**不做 P99、SLO 或 Goodput 结论**。
- **用例输入的诚实说明**：Prompt 由短句重复拼接后截断到固定长度（可能切掉对话模板结尾），并忽略 EOS。长度相同才可比，内容不同才能让串台暴露在序列上——八条一样的 Prompt 即使读错历史也会一致。**这些输出只用于计时，不作质量样本。**

### 2026-09-22 G6-B 任务二云端基线（3090）：批量每轮墙钟几乎不随 B 增长，完整 Prefill 把一轮拉长 4.6~13.8 倍

- **作者**：平台q（被测提交 `9e6ca8a`，设备 3090 24 GiB，torch 2.5.1+cu124，历史 512 Token、64 个纯 Decode 轮、重复 3 次）
- **实验 A（每轮墙钟中位数，ms；括号内为吞吐中位数 Token/s）**：

| 活动请求数 | 逐条 Decode | 批量 Decode |
| --- | --- | --- |
| 1 | 39.462（25.1） | 同一条路径，39.462（25.1） |
| 2 | 79.211（25.2） | 40.284（49.1） |
| 4 | 158.230（25.3） | 40.740（95.6） |
| 8 | 316.596（25.2） | 41.445（182.3） |

- **形状本身就是结论**：逐条路径严格线性（39.46 × B，B=8 时 316.6 ms），批量路径几乎平坦（39.46→41.45，B 从 1 到 8 只涨 **5.0%**）。B=8 时每轮墙钟缩短 **7.64 倍**、吞吐 25.2 → **182.3 Token/s（7.2 倍）**；折算边际成本：第 2 到第 8 个请求每个只多花 `(41.445-39.462)/7 ≈ 0.28 ms`，而第一个请求要 39.5 ms。这就是"读一遍 16.4 GB 权重服务多个请求"的直接体现，也是 G6 立项的物理动机第一次被测到。
- **但离带宽下限还有距离**：单请求每轮 39.5 ms，而权重过一遍的推算下限约 17.5 ms（16.4 GB ÷ 936 GB/s，**推算未测量**），仍差约 2.3 倍。本轮能确认"批量把这层非带宽开销摊薄了"，**不能**确认它是什么——每步 36 层的块表新建与上传、MLP 算术、启动空隙都在其中，未做定位。
- **抖动如实记录，且未归因**：重复之间的中位数极差两条路径都很小（≤0.70 ms），所以中位数可信；但逐条路径的**单次内轮间极差**随 B 迅速变大（B=2 为 40.5、B=4 为 120.4、B=8 为 303.8 ms），而批量路径稳定在 1.7~2.0 ms。逐条路径的轮间抖动来源本轮没测（分配器抖动、一次性冷启动或降频都可能），**不得记到内核头上**。
- **实验 B（Prefill 插入干扰）**：4 个活动请求批量解码的基线每轮 40.8 ms。第 32 轮插入一个完整 Prefill 的新请求：输入 512 Token 时那一轮 **188.9 ms（4.6 倍）**，输入 2048 Token 时 **564.5 ms（13.8 倍）**；两个数同时也就是新请求从提交到首 Token 的墙钟（容量配足、当轮即接入，**不含排队**）。扣掉基线后 Prefill 净耗时约 148 ms 与 524 ms，随输入长度近似线性。
- **这组数就是 G6-C 的输入**：切块的收益上限是"把一轮 188.9/564.5 ms 的停顿摊成若干轮多花一点点"；代价是同一份 Prefill 工作摊到更多轮之后，**新请求自己的首 Token 时间会变长**。所以 G6-C/G6-D 必须同时看"原有请求被拉长的间隔"和"新请求 TTFT"这两个数，只优化一个会得到误导性的结论。
- **口径与前置检查**：每轮墙钟就是每个请求两次输出之间的间隔；吞吐 = 本轮推进请求数 ÷ 每轮墙钟；**批量轮次 ÷ B 是吞吐折算，不是用户 TPOT**。B=8 测量前先跑计时外结果检查，已通过（批量与单独运行的 5 个 Token 序列一致）——没有把"B=4 通过"外推。
- **边界（不得当作更大范围通过）**：只覆盖 BF16 + 默认 V1 内核 + 单卡 + 历史 512 Token + 64 步 + 重复 3 次；未覆盖 INT8/V3 多请求、更长历史、自然 EOS 停止、真实到达过程的多用户负载，也没有取消/超时与 Chunked Prefill。数字包含每步新建并上传 36 层 `[B, 行宽]` 块表与 `starts` 的已知技术债，G6-E 收敛成可复用缓冲后同组实验必须重测才能比较。样本只有 3 次，**不产出 P99、SLO 或 Goodput 结论**。
- **结论归属**：以上是正式性能数字，"G6-B 是否算具备基础 Continuous Batching 能力"与"是否据此宣布阶段通过"按协作约定交主审裁定，我不自行宣布。G6-C 由主审实现，本轮不动 `runner.py:123` 的 Prefill 快路径，也不实现切块。

### 2026-09-22 G6-C 合作式取消与超时（已实现，本机未运行任何检查）

- **作者**：平台q
- **接口**：`Scheduler.submit(..., deadline=None)` 接受调用方同一进程 `time.monotonic()` 上的**绝对时刻**；`Scheduler.cancel(request)` 只做标记；`step()` 起点读一次时钟并处理两者。`deadline=None` 完全保持原有路径。只接受本调度器 `submit()` 返回的 Request——这是调用契约，不为此建全局注册表，也不做逐轮归属扫描。
- **生效边界**：取消与到期只在轮次边界起作用，**不打断已经发出的 GPU 工作，也不加 `cuda.synchronize` 去模拟硬实时**；轮内到期的请求在下一轮起点才被观察到，因此可能多拿到本轮 Token。已有停止原因不被到期覆盖，对 FINISHED 再取消无作用。
- **记账**：WAITING 从未计入 `reserved_blocks`，所以 `_retire` 按**退休前状态**决定是否扣额度；不能用"KV 长度 > 0"判断——整段 Prefill 的请求在第一次前向之前长度同样是 0，那样会误扣。释放仍只发生在 `_retire` 一处；被停下的请求先从容器摘出、再统一退休，每轮只交回一次 `finished`；重复取消与反复 `step()` 不重复扣、不重复归还。等待队首被停后，同一轮的准入就能取到后面的 FIFO 请求。
- **停止原因可区分**：`已取消` / `已超时` / `EOS` / `达到生成上限` 四种共用同一条退出路径，没有第二套实现，也不积累已完成请求列表。
- **验收 `check_stop`**（集中在 `check_chunked.py`，不新建框架）：容量取"一条长请求 + 一条短请求"，让"等待"与"被队首挡住"必然出现而不靠 Prompt 长度碰运气；等待、Prefill、Decode 三处各取消一次；等待到期用**已经过去的时刻**、活动到期用**比一轮前向更早到期的时刻**，全程不 sleep。断言覆盖：未提前选词、额度分文不差、新请求复用到刚归还的块、邻座对照请求与单独运行**逐 Token 相等**、正常结束的原因仍是"达到生成上限"、重复取消已完成对象后额度依旧归零且每层块全部归还。
- **本机验证到哪一步**：只做 `py_compile` 与 AST 解析，未导入 torch、未运行模型或 GPU（本机无 CUDA）；上面所有断言都还**没有跑过**。
- **待云端**：`python -m ampere_kv.check_chunked`（含新增合作式停止用例）与 `python -m ampere_kv.scheduler`（整段路径既有回归，用来证明默认 `deadline=None` 未改变原行为）。本轮不改数值路径、扩展未动，**不需要 `make build`**，也不重跑性能矩阵。
- **未做**：线程与异步控制面、硬实时超时、抢占、换出、跨流回收、错误恢复框架；不中断已发起的 GPU 工作。
- **边界**：G6-C 收尾要求"生命周期取消/超时证据"，本轮实现加云端通过后才谈得上结项；SLO/P99/Goodput 与 CUDA Graph 仍未验证。

- **接入方式**：`Scheduler(..., mixed=False)` 默认关闭，已验证的分离路径不被替换。打开时轮次起点仍先处理取消与到期，然后在**前向之前多试一次准入**，让正在 Prefill 的块与本轮 Decode 合成一次 `model_forward_mixed`；准入判据照旧用全请求预留额度，本轮腾不出空间就只 Decode、下轮起点再准入——不透支尚未回收的块。
- **一轮的语义没变**：仍至多推进一个块；块长与"是不是最后一块"在前向之前定死；中间块不选词，末块才产出新请求的首 Token，所以新请求不会在同一轮又被 Decode。本轮需要的 B 个（末块时 B+1 个）Token **一次取回**之后才 `_commit`，因此记录到的就绪时间确实晚于整次混合计算——这是实测必须体现的成本，不虚构"注意力算完就已就绪"。
- **回退与可观测性**：活动数超过 `max_batch` 时本原型明确退回既有分离路径，不新建跨组策略；`mixed_rounds` 与 `fallback_rounds` 逐轮累加，报告真实混合轮数，防止开关没生效也报收益。EOS／上限／取消／到期仍共用 `_retire`，完成请求每轮只返回一次。
- **正确性对照 `check_mixed.check_schedule`**：同一负载分别用分离与混合调度跑完，比每请求选词序列、实际 Decode 次数、新请求首 Token 轮次与收尾账目（额度归零、每层块全归还），并确认默认路径下混合轮数为 0。另两个小覆盖：跑满一个混合轮后取消正在 Prefill 的新请求（目标请求不再参与、不得选词；其他排队请求仍可合法进入混合轮，其余请求按各自上限完成），以及活动数超过一批时的回退（回退不计作混合成功）。出现选词分歧时报告轮次与两条序列，不放宽容差、不删检查。
- **性能入口**：`bench_insert` 增加 `executions` 参数与 `--mixed` 开关，在同一进程内交替配对分离/混合，沿用四项指标（插入前实际间隔、插入后最大间隔、新请求 TTFT、全部完成时间），窗口仍从提交时刻起算；每组额外打印实际混合轮数与回退轮数。不带 `--mixed` 时命令、行为与输出与之前一致。
- **本机验证到哪一步**：只做 `py_compile`、AST 与未定义名扫描、`git diff --check`；**未导入 torch、未运行模型或 GPU**。所有断言与数字待云端首次执行。
- **待云端**：`python -m ampere_kv.check_mixed`（含新调度对照）→ `python -m ampere_kv.scheduler` → `python -m ampere_kv.check_chunked`（既有回归）。`csrc/` 未动，**不需要 `make build`**；本轮不重跑 INT8 与内核矩阵。
- **边界**：不接 Graph、INT8 与自适应块长；模型调用变快不等于旧请求 Token 更早可用；若配对没有收益就保留原默认路径，不继续堆优化。
